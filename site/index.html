muir

A simulator of the MIT CADR Lisp Machine that goes all the way down to its chips.

Three engines share one machine: micro with no timing model, rtl with the machine’s timing, chip the full netlist — the 1,844 parts of MIT’s own drawings, wire by wire, every board on both buses among them.

Install Manual Repository on GitHub

What this is

The CADR is the second-generation MIT Lisp Machine, designed around 1978 by Tom Knight, David Moon, Jack Holloway and Guy Steele, and built in small numbers. It is a 32-bit microcoded processor with a 48-bit control store, and it became the basis for the first commercial Lisp machines from LMI and Symbolics.

muir simulates it. It aims at the hardware underneath, far enough down that the software written for the hardware runs: the MIT diagnostics, the console program CC, and a two-machine lashup where one machine debugs another through CC, over the debug cable. That lashup is the acceptance test.

Getting there means rebuilding the machine board by board from MIT’s own drawings and wire lists, and that has an output of its own: netlists held pin for pin to MIT’s lists, part models checked against their datasheets, and a record of which recovered files can be trusted and which cannot.

It is written in Rust and has no crate dependencies. The target is System 100, microcode 323 — the restored last MIT release, recovered from TID/671 in the MIT Tapes of Tech Square project. Alfred M. Szmidt has carried that work forward in LM-3, which maintains the Lisp Machine system software and has gone on releasing systems well past this one. System 304, the current of those, boots here too, with its own pack and its own Chaosnet numbers; microcode 323 is one file across the two. The target stays at System 100 for the console program CC, which calls MAKE-ARRAY in a form System 304 removed and so does not load there — and the two-machine lashup through CC is the acceptance test.

Three engines

An engine is an implementation of the machine at one fidelity level. All three sit behind one interface and reach the same architectural state at every microcycle boundary, so you can run the fast one and check it against the slow one. They differ in how much of the hardware they compute on the way, and in where that state sits: micro and rtl hold the scratchpads and the control store as arrays, chip holds them in the RAM chips’ own cells, and the cosimulation compares the two word for word.

The shortest way to tell them apart is by time.

micro has no timing model. It has a clock — it adds up the microcycle periods, so that the devices that read time see it pass — but nothing in it happens at an instant or waits for one. A bus cycle completes at once; the word is in MD two instructions later whatever the memory is doing. It is the engine for what needs no timing: unless a program reaches the hardware directly, or the debugger and the diagnostic bus are in play, micro is enough. It is also much the fastest.

rtl is the timing model. Every datapath signal on the machine’s own two-phase clock, and everything that is a matter of when: the bus’s waits and hangs, the interface’s arbitration and timeouts, a device answering late, the debug cable to a second machine. The boards behind the cables are behavioural models, timed to the nanosecond against the netlist boards. Anything micro cannot do, rtl can; it is slower than micro and still faster than the machine itself.

chip is the full netlist. The parts themselves, resolved net by net from what is actually driving each, and every board on both buses a netlist too. It is the reference: where it and rtl disagree, the drawings decide which is wrong, and it is usually rtl. It is also much the slowest — approximately 4,000 times slower than the hardware.

Those figures count microcycles, and the disk is not in them. With the disk controller as a behavioural model — which is what micro and rtl always use, and what chip uses unless told --disk-controller netlist — a transfer completes inside the instruction that starts it and a seek takes no time at all. A real CADR spent milliseconds on a seek, and spent them executing the microcode’s polling loop: a 55 ms seek is some 380,000 microcycles that produce nothing. muir does not execute them. So on anything that touches the disk muir gains twice over the hardware, once per microcycle and once by having far fewer of them, and by how much depends entirely on how much the program seeks. It is not in the numbers above and it is not worth guessing at.

The netlist disk controller is the exception, and it runs the other way. There the drive takes its own time over every block, so those 380,000 polling microcycles are executed for real, through every gate on the board. A seeking program on that path is slower than the 4,000 figure rather than faster.

What each of the three actually computes on the way to the next microcycle is in the manual.

EngineWhat it computesRate
micro No timing model. One step per microinstruction, on the machine’s own periods but without its bus waits. Fast enough to get somewhere and see what happens. 107 M/s
rtl The timing model. Every datapath signal, on the machine’s own two-phase clock, with the real memory cycle in nanoseconds: MEMSTART, MEMRQ, MBUSY, the acknowledgement back, and the clock held off by WAIT and HANG meanwhile. 16 M/s
chip The full netlist. The parts themselves: 985 of them on the processor and control-store boards, sorted into levels, on four-valued nets, with the bus interface, main memory, the I/O board and the TV as netlists behind the cables. This is the reference the other two are checked against. 1,900/s
The 1,900/s above is the chip engine with every board a netlist. Any board can be run instead as the behavioural model the rtl engine uses, one at a time, which is faster. Which model each engine uses for each part of the machine, and which flag changes it, is a table in the manual.

What a netlist means here

A netlist is the board itself: every part, every pin, every wire between them. These are not drawn by hand and not transcribed from scans. They are extracted from MIT’s own SUDS drawings — the CAD files the machine was designed in — and then held, pin by pin, to MIT’s own wire list for the same board. Where the two disagree, a test fails. Six of the eight boards are checked that way; two have no wire list on the tapes and are held to MIT’s specification instead, which is a weaker thing. Where the netlists come from sets out the whole chain, file by file, and says which board is checked which way.

Underneath, a part is a behaviour checked against its datasheet, nets resolve four-valued so that an open-collector bus works the way it does on the board, and the parts are evaluated in level order, with only the ones something moved under recomputed.

A part is one device at one board location — the chips, the oscillators, the delay lines, the switches, the LED digits — and not the bypass capacitors, resistor packs and busbars beside them, which nothing here computes. The files list gates rather than devices and run longer than the boards do: the processor’s 985 parts arrive as 1,243 part records, a quad NAND being drawn four times under the one designator. A whole machine is 1,844 parts with one memory board on the Xbus and 7,052 with all thirty-two.

Six of the seven files are one card each — the same card, six rows of thirty positions, with 176 to 180 of them filled, which is why those boards land within a few parts of each other — and the processor and the control store are the two large boards, their designators running in four sections and in two. MIT counted these boards twice itself, by the locations it stuffed and by the packages each part type takes, and every board but the SIMPLE TV has one of those counts or both to answer to.

The Chaosnet interface shares the I/O board rather than having one of its own, and MIT drew the two separately: fourteen pages for the board proper and thirteen for Chaosnet. All twenty-seven are in the netlist, 94 parts against 84, five chips having gates on both sides. The interface runs: it knows its own address off the switches, a packet written into its transmitter comes back out of its receiver with the check word right, and it trades packets with the Chaosnet server beside it — muir’s stand-in for the servers on its associated machine, OZ — taking broadcasts, passing over other hosts’.

Why the level matters

A model that steps once per microinstruction is self-consistent, agrees with itself, and boots Lisp. It is still not the machine, and one instruction shows the gap.

The boot PROM notices. CLEAR-I-MEMORY writes all 16,384 words of the control store, so the shortcut is taken 16,384 times, and two microcycles apiece is 32,768 of them — six per cent of the boot, out of one instruction.

To the first disk readExecuted instructionsMicrocycles
micro, one step per microinstruction416,736505,079
rtl, following the drawings416,736537,848
The same instructions either way, so nothing an instruction trace can ever see. A cycle count built on the first number is simply wrong, and an instruction trace cannot reveal it, because the cycles that were inhibited leave no instruction behind.

The machine it models

The processor is not one board and the bus interface is not part of it. They live in different backplanes and talk over five 40-wire flat cables that carry two independent buses and the master clock, which the processor supplies. Everything else in the machine hangs off one of those two buses.

Installing

No binaries are distributed; you build it yourself. A fresh clone needs nothing else: everything is committed, there are no crate dependencies, and the parts that want fetched material skip cleanly and say so.

  1. The Rust toolchain

    Install rustup, then open a new shell so cargo is on the path.

    curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

    The compiler version is pinned in rust-toolchain.toml; the first cargo command in the directory installs it, with clippy and rustfmt. Nothing else is downloaded — there are no crate dependencies.

  2. Clone and build

    git clone https://github.com/metebalci/muir
cd muir
cargo build --release

    That builds it. The tests are optional — a fresh clone passes them with nothing fetched, when you want the check:

    cargo test

  3. The System 100 release

    This is what the engines boot from: the disk pack and the system sources. It is not part of muir; the script fetches it from muir’s own mirror of the original release and checks every file against its SHA-256 sum.

    tools/fetch-system-100.sh

    It puts the system sources in vendor/system-100-0/sys/ and the disk pack in vendor/run/, where the tests look for them. Running it again leaves whatever is already there alone. It is POSIX shell; Windows is untested, so use WSL. tools/fetch-system-304.sh beside it fetches System 304, which also boots here — its pack is a different machine and wants --chaos-address 4401,4403.

  4. Run System 100

    target/release/muir --disk-pack vendor/run/disk-sys-100-0.img

    The simulator is the muir binary that step 2 built. It runs one engine from the boot PROM with the pack on the disk controller’s cable, and reports microcycles per second against the machine’s own rate. One engine at a time: --rtl is the default, implied when neither --micro nor --chip is given.

    It wants the disk pack from step 3, named: there is no default pack, and without one the engines wait on a drive that never answers. The Chaosnet addresses are the band’s own, and this band’s — MIT-LISPM-1 at 3050 with MIT-OZ at 3060 — are what --chaos-address defaults to. System 304’s pack is a different machine and wants --chaos-address 4401,4403; a server answering anywhere else is one that band never calls, so it boots but stops to ask for the date and reaches no files.

  5. Benchmark

    What the three engines cost, on two programs that need nothing fetched — so this one works straight after step 2. Six runs of five seconds each; pass a different number of seconds if you want them shorter or longer.

    cargo run --release --example benchmark
    micro  datapath    532963970 cycles    5.001 s    106581585 cycles/s  15.45x hardware
rtl    datapath     79913610 cycles    5.000 s     15982638 cycles/s   2.32x hardware
chip   datapath         9520 cycles    5.044 s         1887 cycles/s    hardware/3654
micro  control     663839358 cycles    5.000 s    132759460 cycles/s  19.25x hardware
rtl    control      81158805 cycles    5.004 s     16219471 cycles/s   2.35x hardware
chip   control         10101 cycles    5.042 s         2003 cycles/s    hardware/3443

    datapath is every one of the ALU’s sixteen logic functions and four of its arithmetic ones, the output bus shifted both ways, the Q register loaded, shifted and read back, and the byte hardware, each operation taking the last one’s answer. control is calls three deep and back, a call that returns on the POPJ bit, a dispatch through dispatch memory the program wrote itself, and branches taken and not taken. Both are loops with no memory in them, so what is timed is the processor and not a wait on the bus.

    The rate is against the machine’s own 145 ns microcycle. Nothing here is taken on trust: each program counts its own times round the loop and leaves the count where every engine can be read for it, and a run whose count does not match the microcycles it ran prints nothing at all — a machine that has stalled toggles fewer nets and would otherwise look faster.

    The other examples — what is on a pack, what the machine is drawing, how much of microcode 323 the chip-against-rtl comparison covers, and the two-machine lashup by hand — are listed in examples/README.md. Most of them want the pack from step 3.

Sources and attribution

Almost nothing here is a first-hand invention. The machine, the drawings, the wire lists, the microcode and the diagnostics are MIT’s, recovered by other people’s work over decades. The recovered material is also not uniformly trustworthy — it mixes primary MIT files with hand conversions and reconstructions from scans — so nothing load-bearing is taken from a single file: anything that matters is cross-checked against a second copy that reached us by a different route, and a test enforces the agreement. Every netlist in the repository is held pin for pin to MIT’s own wire list for the same board, and where a fact is believed but unchecked the code that depends on it says so.
